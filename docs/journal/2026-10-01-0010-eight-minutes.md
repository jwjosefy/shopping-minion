## The web app (M2)

The LLD for M2 went through two rounds of questions in Obsidian before I approved it, around 16:15. Then two waves of Sonnet tasks, each reviewed before merge, and by 18:00 it was done:

- **FastAPI and Vue,** no build step. One worker thread owns the browser, and a state machine walks the run through reading the list, my review, searching, Jev, my picks, my cart review, and filling the cart. The screens follow it over server-sent events.
- **The phone is the main screen.** The server listens on the LAN with a random token, and prints a QR code in the terminal and on the desktop page. I scan it and take the photo of the list right there.
- **The first try from the phone failed** because of my own firewall. One `ufw` rule, LAN only, port 8000.

Integration found three small things: the list photo had to come from the server, the pick counter from the backend, and the guard that searches the code for anything that could place an order now also searches the web files. My verdict after runs 6 and 7, from the desktop and the phone: *ficou muito bom*. Room to improve, no glaring bug.

## Measuring it (M3)

M3 existed to answer the question behind the whole project: is it faster? The first end-to-end run had shown it *works*, but nothing recorded how long each part took. The run history only kept when a run started.

There was a subtler gap too. When I picked a product, the app overwrote Jev's decision with mine. So "I agreed with Jev" and "I chose something else" looked the same afterwards. The fix was a small append-only log per run, with every state change, every pick (with Jev's original choice next to mine) and every cart edit, and a `report` command that reads it.

- **Cart:** no quantity changes, nothing removed. 28 of 28 products checked against the reloaded cart.

The report is the starting line for M4. 25 manual picks out of 32 items is still the expensive part, and in 13 of them Jev was already right, just not sure. That is exactly what preferences from my history should fix.

## Working with someone else

Peter, my son, the one I built the first prototype with, wants to work on this with me. The first question was how to share the repo without sharing my secrets.

The answer turned out to be: don't share the dotenvx key at all. The `.env` is committed encrypted to a public repo, so the key opens every secret in it, in every old commit too, including my store login. Once handed over, it can't be taken back. The only undo is changing every secret at its source. And Peter doesn't need any of it: the app only needs a Jev key, and Peter is the one who gave me mine.

So each person brings their own: their key in a git-ignored `.env.local`, their store login, their Claude Code for the OCR. To make that one command, the repo now has a `justfile` (`just jev`, `just login`, `just up`, `just report`) and a bootstrap script that installs uv, just and dotenvx without sudo:

```bash
curl -fsSL https://raw.githubusercontent.com/jwjosefy/shopping-minion/main/scripts/bootstrap.sh | bash
```

One small thing I caught in review. Claude's first `just jev` read the key with `read -s` and passed it to dotenvx on the command line. `dotenvx set KEY` with no value already prompts for it, masked, so the key never touches the shell. Simpler and safer. I tested it, and it's what's there now.
